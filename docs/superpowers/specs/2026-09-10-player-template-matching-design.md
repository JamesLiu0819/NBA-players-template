# 設計文件：10 人球員模板對照表（L3 匹配層最小版本）

用途：這份文件記錄「10 人球員模板對照表」這個子功能的設計決策跟理由,給之後寫實作計畫跟回頭查決策脈絡用。
可手動調整的變數：無——這是設計文件,不是程式或資料。

- 日期：2026-09-10
- 狀態：待使用者審閱
- 對應 SPEC.md：§2 (L3 匹配層)、§3.1 (差異 argmax)、§3.4 (球員庫)、§6 (球員資料庫建置)、§9-4 (10人對照表)
- 對應 CLAUDE.md：`/data/players.json` 是離線建置產物、`/src/engine` 純函數規則、每份檔案開頭要有繁體中文用途/可調變數說明

## 1. 背景與目標

目前系統已經有 L1(技能向量)、L2(四軸座標)、L4(優先序)三層的最小版本可以跑。這次要做 L3(模板配對層)的最小版本：**只做 10 人對照表**,不做 3 位深度模板、不做反面對照、不接影片庫。

動機（使用者原話整理）：不是每個人都有在打正式比賽,所以「環境權重 + 訓練優先序」那條路線不是每個使用者都適用；但「你的座標離哪些現役球員最近」這個定位/模板配對的價值,不需要環境資料就能成立,先把這塊做完比較實用。

## 2. 範圍

**這次做：**
- 一份小規模(約 20 位)手動估算的球員種子資料
- 純函數：給定使用者四軸座標 + 球員清單,算出最近的 k 位球員(含距離、差異向量、差異最大軸、貼合度星級)
- 一支文字報表腳本,套用固定模板產生「10 人對照表」（排序、球員、相似處、差異、最值得學的一件事、貼合度）
- 對應單元測試(TDD)

**這次不做（明確排除,留給以後）：**
- 3 位深度模板（技能最貼合/身體最貼合/天花板方向）——需要先有能穩定運作的最近鄰查詢,下一步再疊規則
- 反面對照——需要 learnability_flag 的判斷邏輯,下一步再做
- 影片庫串接
- 真實 NBA 數據抓取(nba_api / Basketball-Reference)——這次先用手動估算 seed,之後才換真數據
- 環境權重、訓練優先序整合——這次的 10 人對照表跟 P_i 公式無關
- 座標軸加權距離——先用不加權歐幾里得距離,理由見下一節
- 任何前端 UI

## 3. 關鍵設計決策

### 3.1 資料來源與生成方式

**決策**：手動估算約 20 位現役球員的四軸座標,寫成 `scripts/build_players_seed.py` 裡的常數,跑這支腳本產生 `data/players.json`。

**為什麼不直接手寫 `data/players.json`**：CLAUDE.md 明確規定 `players.json` 是「離線建置產物,勿手改,改 scripts/」。即使資料本身是估的,也要透過腳本產生,這樣之後要換成 nba_api 真數據時,下游(engine、報表腳本)完全不用動,只要換掉 `build_players_seed.py` 裡的資料來源邏輯。

**估算依據**：可以參考 NBA2K 屬性值、公開球評文字描述、Basketball-Reference 的公開數據當手動判斷的參考,但**不寫自動化爬蟲**去抓 NBA2K(法律風險,已跟使用者確認過)。每位球員的 `_estimate_basis` 欄位要註明參考了什麼、用什麼方式估的。

**球員挑選原則**：覆蓋 A/B/C/D 四軸不同象限(例如：純外線射手、純禁區苦工、全能持球核心、頂級運動能力側翼等),讓最近鄰查詢在不同使用者輪廓下都有合理的候選,而不是 20 位都長得很像。

### 3.2 距離公式

**決策**：不加權歐幾里得距離。

```
distance(使用者, 球員) = sqrt(Σ (球員[軸] - 使用者[軸])²)   對 A, B, C, D 四軸
```

**為什麼不加權**：D 軸(運動能力)該不該打折,本質上跟 `env_weights.json` 一樣是一個需要領域專家決定的校準參數。現階段不引入第二個未決的校準旋鈕,先確認「距離→排序」這條管線本身合理,之後如果黃金案例配對結果感覺不對,再回頭調整加不加權。

### 3.3 差異軸與貼合度星級

**差異軸**（對應 SPEC §3.1）：`argmax(球員[軸] - 使用者[軸])`,對 A/B/C/D 四軸取**帶符號**的差,不取絕對值——找的是「球員比你強最多的那個方向」,也就是「你該往哪個方向補」。

- 已知邊界情況：如果使用者在四軸都贏過某位球員,這個算法還是會回傳一個「差距最小的負值」軸,語意上不是「該補的方向」。這次不特別處理(球員種子資料選的是現役球員,實務上不太會發生使用者全面超越),但會在 engine 函數的 docstring 跟測試裡明確記錄這個已知限制,不假裝它不存在。

**貼合度星級**（固定門檻,可調參數見下方檔頭說明）：

| 距離範圍 | 星級 |
|---|---|
| ≤ 20 | ★★★★★ |
| ≤ 40 | ★★★★☆ |
| ≤ 60 | ★★★☆☆ |
| ≤ 80 | ★★☆☆☆ |
| > 80 | ★☆☆☆☆ |

這組門檻是依常理暫定的(跟環境權重、距離加權一樣的性質),之後有真實球員資料庫、知道實際距離分佈長什麼樣子後,應該重新校準。

### 3.4 「相似處」跟「最值得學的一件事」怎麼做到具體不空泛

SPEC §9 明確要求「相似處...具體到技能與身體條件,不寫空泛形容」跟「最值得學的一件事...只能一件,且必須可執行」。這兩項是文字輸出,但**產生方式必須是固定模板 + 結構化資料組出來的,不是即時生成的自由文字**（符合 CLAUDE.md 規則 1：分析必須確定性,AI 只能用在事後潤飾,不用在這裡）。

做法：
- 每位種子球員資料裡有 `notable_traits`(2-4 條具體短句,例如「擅長無球跑動接球即投」,不是「投籃很準」這種空泛形容)跟 `signature_skill_id`(對應到現有 5 項關鍵技能之一,可為 null)。
- 「相似處」＝直接列出該球員的 `notable_traits`。
- 「最值得學的一件事」＝**只有當球員的 `signature_skill_id` 所對應技能,其自己的 `axis_relevance` 向量裡權重最高的軸,恰好等於差異軸**,才用固定句型引用 `skills.json` 裡該技能的 `metric.action`(已經是具體可執行的描述,例如「定點接球投三分」);其他情況(包含沒有 `signature_skill_id`,或該技能的主導軸跟差異軸不同)都用差異軸的固定句型(例如「差在 B 軸(空間位置)→可以多練習跑到外線接球出手」)。

**一個規則性的結果,先寫明白避免之後被誤認為 bug**：D 軸依 SPEC 設計視為不可習得,所以現有 5 項技能的 `axis_relevance` 都沒有把 D 列為主導軸(各技能的主導軸分別是 B、A、A、C、C)。這代表**差異軸落在 D 時,一定會走「差異軸的固定句型」這條路徑**,絕對不會誤套某個技能的 `metric.action`——這是刻意的設計結果(D 軸差距大代表「天花板方向」,本來就不該建議去「練」一個不可習得的東西),不是需要修的漏洞。

## 4. 檔案與模組

```
scripts/build_players_seed.py   手動估算的球員資料(常數)→ 產生 data/players.json
data/players.json                離線建置產物(不手改),約 20 位球員
src/engine/player_matching.py    純函數：rank_similar_players(user_coordinates, players, k=10)
scripts/run_player_match.py      讀 answers.json + players.json → 印出 10 人對照表文字報表
tests/engine/test_player_matching.py   rank_similar_players 的單元測試
tests/engine/test_players_data.py      players.json 的資料完整性測試
```

所有新檔案開頭都會照現有慣例加繁體中文的「用途」跟「可手動調整的變數」說明。

## 5. 測試計畫

- `test_player_matching.py`(TDD,跟之前一樣先寫測試再實作)：
  - 距離計算正確性(已知座標算出已知距離)
  - 依距離排序、k 截斷、players 數量 < k 時不報錯
  - 差異軸 argmax 的正負號行為(包含「使用者全面領先」的已知邊界情況,明確測試它回傳什麼而不是假裝不存在)
  - 貼合度星級門檻邊界值(19/20/21、39/40/41...)
- `test_players_data.py`：
  - `players.json` 至少有 10 位球員(否則 10 人對照表湊不滿)
  - 每位球員欄位齊全、座標在 0-100 範圍內、id 唯一
  - `signature_skill_id` 如果不是 null,必須對應到 `skills.json` 裡存在的技能 id
